# 第二阶段：让同一个模型跑得更快

[回到总览](../../README.md) · 上一阶段：[从文本到模型](../01-basics/README.md) · 下一阶段：[数据与规模](../03-data-scaling/README.md)

**状态：尚未实现。下面说明要做的任务与顺序，不是已经取得的实验结果。**

## 1. 任务是什么，有什么意义

第一阶段证明“模型能算、参数能更新”。这一阶段问：**同样的计算能不能花更少时间、更少显存？增加 GPU 后到底快了多少？**

要交两类证据：自己写的注意力 GPU 计算程序，以及单卡 / 多卡的真实对照。不能只说“支持多卡”，必须说明相同条件下时间、内存和吞吐变化。

## 2. 名词是什么意思

| 名词 | 通俗解释 |
| --- | --- |
| GPU | 适合并行执行大量数值运算的处理器。 |
| 显存 | GPU 保存权重、中间计算和输入输出的内存；不等于硬盘空间。 |
| Kernel，计算内核 | 在 GPU 上运行的一小段计算程序，不是操作系统内核。 |
| Triton | 编写 GPU 计算程序的语言与工具。本阶段用它自己实现第一阶段的注意力计算。 |
| Attention，注意力 | 从前文各位置按相关性取信息的计算，第一阶段已经解释；这里改实现方式，不随意改其数学含义。 |
| 性能分析 | 先测时间花在哪里，再决定改哪段代码；不是凭感觉重写所有模块。 |
| 多卡训练 | 多张 GPU 协作计算梯度和更新模型。需要交换数据，卡数翻倍不保证速度翻倍。 |
| 推理 | 不再更新权重，而是用模型生成结果。它的性能问题与训练不同。 |
| 吞吐 | 每秒处理多少 token 或请求。处理量大不代表单个用户等待更短。 |
| 延迟 | 一次请求等多久；可区分等到第一个 token 的时间和后续每个 token 的间隔。 |
| KV cache | 生成时缓存以前算过的注意力信息，避免每次重新算全部前文；空间换时间。 |

## 3. 先做什么，后做什么

1. **保留第一阶段的正确参考实现。** 固定模型大小、输入长度和数值精度，测各段耗时与显存，找出瓶颈。
2. **写 Triton 注意力内核。** 先让计算结果和参考实现一致，再验证训练时的梯度也一致，不能只测“能返回一个张量”。
3. **做单卡对照。** 在不同输入长度下重复运行，比较时间和显存；先做预热，让首次编译和初始化不混进稳定耗时。
4. **测多卡训练。** 先保持总批量一致，再明确比较训练速度；记录 GPU 型号、数量及卡间连接，避免把硬件差别当算法增益。
5. **单独测生成。** 固定输入和输出长度，分别记录首字等待、后续生成间隔与总吞吐。训练加速不自动等于生成加速。

## 4. 为什么用这个方案

先做正确的慢版本，再替换内部计算，才能把结果变化归因于优化。注意力涉及大量中间数据，减少它们在计算与内存之间搬运，有机会同时省时、省显存；是否划算仍需实测。

多卡带来更多计算资源，也带来通信成本。分别控制“总工作量”和“每卡工作量”，才能说清是单次任务加速，还是能处理更多任务；不把两者混为一谈。

## 5. 效果怎样，怎样才算做完

**现在没有 Triton 或多卡实测结果。** 当前 Mac 的 MPS 训练不能冒充 Linux / NVIDIA CUDA 环境的 Triton 与多 GPU 实验。

完成时应在本篇填入：参考版与优化版的误差、单卡时间 / 显存、多卡训练加速比，以及生成延迟 / 吞吐。加速比是“旧耗时 ÷ 新耗时”；还要说明重复次数与波动，失败或无收益的设置也应保留。

本阶段输出更高效、可信的运行工具，供后面的数据和规模实验反复使用；不要求为了测内核先训练好一个能聊天的模型。
